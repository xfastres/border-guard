## 总体判定：**CONCERNS**（仅针对视觉契约）

10 项视觉契约中，**7 项完全符合，3 项带存疑点，0 项硬性失败**。渲染层（`L4341–5268`）、主题 CSS（`L369–575`）、`GLYPHS` 图标表（`L5620–5650`）三大块均已落地且相互对齐，方向与 §0 参考图一致。存疑点集中在：① 白天暖光渐变缺少 §5 要求的能力检测（唯一实质性技术契约偏差）；② 城墙「受击闪白」的作用对象与验收口径需澄清；③ 细节标识（角标文字、状态气泡、耐久牌数字）在 50% 缩放下的可读性无法靠静态判断。另有 1 处代码注释与实现不符（耐久牌「上沿/下沿」）和若干结构层面的低风险提示，均列在下文。

判定图例：**符合** = 代码已实现且与契约一致；**存疑** = 代码实现了但存在口径/健壮性/可读性上的不确定，需截图或主理人确认；**不符合** = 契约未被满足。

### 2. 生产建筑轮廓 / 角标 / 箭塔顶色 — **符合**

`structure()`（`L4601–4683`）为 `if/else if` 链，各分支构图明确不同：

| 建筑 | 剪影特征 | 位置 |
|---|---|---|
| 农场 `farm` | 红顶谷仓（`houseBox`）+ **旋转四叶风车**（细高竖杆）+ 麦田 | `L4613–4627` |
| 林场 `lumber` | 木屋 + 三颗圆木（同心圆）+ 松树 + 树桩斧头 | `L4628–4637` |
| 采石场 `quarry` | 低平灰岩多边形坑 + 切方块 + **L 形起重架** + 吊石 | `L4638–4649` |
| 矿场 `mine` | 高三角山体 + **黑色拱形矿口** + 木支护 + 铁轨/矿车 + 矿点 | `L4650–4664` |
| 箭塔 `else` | 细长梯形石基 + 平台 + **尖三角顶** + 旗杆/旗 | `L4665–4681` |

- **没有一个生产建筑被画成箭塔**：`PRODUCTION_TYPES = {farm:'farm', wood:'lumber', stone:'quarry', mine:'mine', rich:'mine', iron:'mine'}`（`L2462`），`develop()` 用它生成 `t.building.type`（`L3055/3069`），四种生产 type 各自命中专属分支；只有 `BUILDS` 中的 `tower`（`L2459–2461`）才走 `else` 箭塔。绘制契约测试 `tests/v029-workplaces.test.cjs:164` 明确断言 `row.tower === false`（`L164`），`:156` 断言 `type && type!=='tower'`。
- **富矿 / 铁矿角标**：`L4652–4653` 读 `t.node?.kind` 决定 `tint`（iron `#a9b9c4` / rich `#ffd257`），`L4663` `if(ore==='rich'||ore==='iron')` 画深色圆角底牌 + `label('富'/'铁', ..., 9, tint)`。矿点、矿车内矿石也用同一 `tint` 着色（`L4660/4662`）。
- **箭塔升级换顶**：`L4673` `const roof = lv===2 ? '#6a5aa8' : lv ? PAL.roofRed : PAL.roofBlue` —— lv0 蓝顶、lv1 红顶、lv2 紫顶；`L4679` 另有 `Ⅱ/重` 等级字样，`rework()`（`L3124`）为升级入口。

> 结构提示（非不符合）：`structure()` 的 `else` 是「无类型兜底 = 箭塔」，若未来新增未登记的 `building.type`，会静默被画成箭塔。当前 type 集合（castle/wall/farm/lumber/quarry/mine/tower）全部覆盖，无风险。

### 3. 开发后清除旧自然图标 — **符合**

四重保险，逻辑闭环：

1. `develop()`（`L3053–3076`）：`clearTileCover(t)`（`L3061`）把 `trees/rock` 的 `ground` 改回 `grass`、`cover='none'`（`L820–824`）；`t.field=false`（`L3062`）；`t.node.developed=true`（`L3063`）；`t.building={type,...}`（`L3069`）；**`invalidateNavigation()`（`L3071`）触发地形缓存重绘**。
2. `nodeArt()` `L4686`：`if(t.node?.developed) return;` —— 已开发直接返回，不叠画树/石/麦田资源图标。
3. `drawFoliage()` `L4527–4540`：内部按 `revealedNode=t.visible&&t.node` 抑制；更关键的是 `draw()` `L5215` 的调用前置条件 `if(!t.node?.developed && (t.ground==='trees'||t.ground==='rock'))` —— 开发后**根本不入 sprites 队列**。
4. `draw()` `L5223` `if(t.visible&&t.node&&!t.node.developed) … nodeArt`；`L5224` `if(t.building) … structure` —— 只排队生产建筑。

`terrain()` 内 `L4486 if(t.field&&!t.node) wheatPatch(30,32)`（麦田底纹）：开发后 `field=false` 且 `t.node` 仍存在，条件不成立，不会残留麦田；农场自身的麦田由 `structure` farm 分支 `L4616` 重画（属建筑本体，符合「只显示对应生产建筑」）。

绘制契约测试 `tests/v029-workplaces.test.cjs:160–164` 对每个已开发节点断言 `structure=true / nodeArt=false / foliage=false / tower=false`，与上述代码一致。

### 6. 光照与水波 — **符合 + 1 处不符合（技术契约）**

`drawLighting(isNight)` `L5042–5077`：

- **白天叠暖光**：`L5043–5047` 用 `ctx.createLinearGradient` 生成 `rgba(255,240,190,.10) → rgba(40,70,30,.08)` 全屏叠加 → 符合。
- **夜晚蓝色暗幕**：离屏 `lightCanvas`，`l.fillStyle='rgba(14,24,56,.58)'` 全屏（`L5057`）→ 符合。
- **四处光孔**：`destination-out` + `hole()` 径向渐变（`L5060–5064`），分别开在**主城** `L5066`、**领主** `L5067`、**箭塔** `L5068`、**营地** `L5069` → 符合，与契约列出的四个光源一一对应。
- **叠暖色火光**：`L5071–5076` `globalCompositeOperation='lighter'` + `warm()` 径向渐变 `#ffaa46`，主城 `L5074`、箭塔 `L5075` → 符合。
- **能力检测（夜分支）**：`L5050 if(!lightCanvas.getContext) return;`、`L5054 if(!l \|\| typeof l.createRadialGradient!=='function' \|\| !l.createRadialGradient(0,0,0,0,0,1)?.addColorStop) return;` —— 对离屏画布与 `createRadialGradient` 双重检测，正是 §5 要求的范式 → 符合。测试桩 `tests/helpers/v029-vm.cjs:102–109` 中 `createRadialGradient` 返回空函数，会命中 `L5054` 提前 return，夜晚光照整体跳过，不会抛异常。

> ⚠️ **不符合（§5 技术契约，本轮最关键发现）**：**白天分支 `L5044` 的 `ctx.createLinearGradient(...)` 未做能力检测**，紧接着 `L5045` 直接调用 `g.addColorStop(...)`。§5 明确要求「新加的绘制只要用到渐变或离屏画布，都要像 `drawLighting`/`cachedLayer` 那样做能力检测后再用」。

### 6.2 两条阻塞项裁定（WP1 质量门）

#### A. 「受击闪白」→ **符合契约，不是阻塞项，不需要修复**（建议作为已知取舍写进 WP5 报告）

**原文核对**（`docs/v030-handoff-plan.md` L46，逐字）：
> 整圈城墙：先画投影、描边、墙身和高光，再画雉堞、按耐久出现的裂纹、拐角塔楼、竖立的门楼。全圈只有一块耐久牌，放在圈下沿，受击时闪白；倒塌后画碎石残段。

**理由（三条，逐层递进）**：

1. **句法主语是「整圈城墙」，不是耐久牌**。整段以「整圈城墙：」起头，其后全部谓语（先画…再画…只有一块…放在…受击时闪白；倒塌后画碎石残段）共享这一主题。分号后的「倒塌后画碎石残段」主语无可争议是城墙整体——「受击时闪白；倒塌后画碎石残段」是**并列对称的城墙两种状态表现**。若作者意在「耐久牌闪白」，应断为独立句且不会与「倒塌后画碎石残段」用分号并列。「放在圈下沿」是对耐久牌数量/位置的插入说明，不改变全段主语。
2. **§4.4 视觉清单未把闪白列为验收项**。§4.4 五条中涉及城墙的只有「40 个敌人时单位和血条仍可分辨」；§0 核心规则表涉及城墙的只有「整圈共享耐久，归零整圈倒塌」与「破墙后主城很快失守」。闪白只出现在 §1.2 对渲染层的**描述性文字**里，不是验收断言，也不在 WP1 验收清单（§3 WP1）中。用它去卡 WP1 质量门属于把描述当断言。
3. **实现与核心规则语义一致，且是更优的反馈设计**。`L4892` 让 `body`（**所有 edges 共用**）在 `L4891` 的 160 ms hitFlash 窗口内变 `#fff1c8`——闪的是**整圈墙身**，正好表达「整圈共享耐久被击中」，与 §0「整圈共享耐久」一一对应。受击位置在墙，反馈就该落在墙；耐久牌是常驻 HUD 读数（含 hpPips 与 `hp/maxHp` 文字），让它闪白会降低数字可读性，反而是更差的设计。另 `L4955` 在 `ratio<.35` 时把耐久牌边框转红 `#ff7a5a`，已提供耐久牌侧的低耐久警示，并非「耐久牌完全无反馈」。
4. **补图 + 像素抽样已把「代码事实」升级为「可量化视觉实证」**。主理人转来 quality-lead 的核验（fx/ 状态夹具，非自然流程证据）：受击时整圈墙身——`L4902` 墙身、`L4917` 雉堞、`L4931/4933` 拐角塔楼——由 `PAL.stone` 变为 `#fff1c8`；**同一世界坐标 [154,92] 的像素** `flashOffRGBA=[92,95,104,255]` → `flashOnRGBA=[115,115,117,255]`，与夜间暗幕 `rgba(14,24,56,.58)` 叠加下 `#c9c0aa` / `#fff1c8` 的**理论值逐通道吻合**。耐久牌（`L4955`）边框色只由 `ratio` 决定，牌本身为**深色玻璃底+金边+白字、不闪白**，仅数字由 `600/600` 变为 `593/600`；`extra/wall-flash-ab-compare.png`（1700×900 并排 A/B）肉眼可见整圈变浅奶白、两侧耐久牌外观一致。即：闪白作用于整圈墙身是**有意且已量化验证的设计**，耐久牌不闪白不是绘制遗漏；HP 数字变化独立承担数值反馈。这消除了 WP1-ART-01「口径待澄清」的最后一点不确定，也让「耐久牌是否也应闪白」不再是一个开放问题——两种反馈已各司其职。

> 补充：像素值 `[92,95,104,255]→[115,115,117,255]` 逐通道吻合是本次复核里证据强度最高的一条，它同时排除了「闪白其实没生效/被暗幕吃掉」的可能；因此裁定 A 不只是文义解释，更有实现层与像素层的双重确认。

**结论**：按 §1.2 与 §4.4 判定为**符合契约**。不是必须修复的阻塞项，**不需要改代码**。建议动作：在 `docs/v030-polish-report.md`（WP5）的「设计取舍」里写一句明确说明——「受击闪白作用于整圈墙身，耐久牌保持常显且仅在低耐久时转红边框」，以防后续包误读 §1.2 而「修」掉正确行为；同时订正 `L4949` 的过时注释（「上沿」→「下沿」），属文档整理、不属功能修复。S8 补图已到位并完成复核，本条**已闭合**。

#### B. 「缩到 50% 仍能分辨」→ **9px/7px 文字标注不纳入该条口径；该条判符合（50% 实拍确认），改进建议归 WP3**

**原文核对**（`docs/v030-handoff-plan.md` §4.4 第一条，逐字）：
> 四种生产建筑、箭塔、主城、营地轮廓各不相同，缩到 50% 仍能分辨

**判定：不纳入**。理由：

1. **原文关键词是「轮廓」**，且明确列举验收对象为四种生产建筑、箭塔、主城、营地**这七类实体本身**。剪影分辨靠的是形状：风车竖杆 / 圆木圆堆 / 直角 L 吊架 / 山体黑拱洞 / 尖三角塔顶 / 三塔群 / 单帐篷——6.1 S1 已实证这些差异在 100% 与 390px 手机端均成立，按形状差异静态判断 50% 下仍成立。富/铁角标、状态气泡、耐久牌数字、箭塔等级字是**叠加在实体上的信息标注层（annotation）**，不是轮廓，把它们塞进「轮廓可分辨」是口径错配。
2. **§4.4 把「轮廓可分辨」与「小元素可读性」分成两条写**：第二条是「40 个敌人时，**单位和血条**仍可分辨」，恰好说明清单作者区分了「形状剪影」与「细小读数」两类要求，且后者只覆盖单位/血条，不含角标/气泡/等级字。§1.2 描述渲染层时也从未承诺这些标注在 50% 下可读。
3. **这些标注不是唯一信息通道，缩小后不构成信息丢失**：城墙耐久在顶栏战斗状态栏（`night-390x844` 可见「城墙 502/600」）与右侧详情面板双血条（`wall-inspect-vitals`）都有冗余；居民状态在详情面板有文字（`desktop-resident-moved`「驻留野外」）；矿种/箭塔等级在 `inspect()` 面板可读。可访问性上属二级信息，不是关键路径。

4. **补图给出了确定事实，且恰好印证「口径分离」是清单作者的本意**。quality-lead 的两档缩放观察（主理人转，最终判定归我）：**100% 下** `600/600` 耐久牌数字与绿色气泡内工具字形**可读**，富矿角标/箭塔等级字虽很小但**仍能定位**；**50% 下**四类小字（9px 富/铁角标、9px 作业气泡、9px 耐久牌数字、7px 箭塔等级字）**均糊成色块不可读**，但**七类建筑一级剪影仍可分辨**。即：把小字纳入会导致「50% 判不符合」，把小字不纳入则「50% 判符合」——而 §4.4 该条的措辞明确只锁定「轮廓」，且清单另有一条专门管「单位和血条」的可读性要求。两者结合只能得出一个自洽读法：**轮廓 = 剪影，标注层不在本条内**。若作者真想让 9px 汉字在 50% 下可读，不可能用「轮廓」二字、也不会把它与「单位/血条可读性」分开列条。

**该条验收判定**：**符合**——依据 `extra/scale-50pct-full.png`（720×450）与 `extra/scale-50pct-castle.png`（240×210）实拍，七类实体剪影在 50% 下仍可逐一分辨（矿场黑拱洞 vs 采石场 L 吊架、箭塔尖顶+旗 vs 矿场山体均不混淆）；100% 对照为 `scale-100pct-full-1440x900.png` / `scale-100pct-castle.png`（480×420）。**S11 补图已到位、本条已闭合**，不受 9px 文字影响。

**但必须登记一个独立的、真实的可访问性问题**：四类小字在 50% 下糊成色块不可读，在 390×844 手机端亦偏小。这是**可访问性/多端可读性缺陷**，不因不纳入本条口径而消失，只是不归 WP1 质量门管。S2 亦据此闭合（见 6.1 S2 行）。

**建议归属 → WP3（布局与多端）**，理由：WP3 已明确处理多视口与手机端可读性（§3 WP3.1 七视口逐一检查「顶栏资源不换行不裁切」「底栏文字不竖排」、WP3.5「手机端资源只显示图标加数字」），同类问题同包处理，且 WP3 已有 7 视口截图流程可顺带取证；不归 WP4（WP4 是表现力/节奏/reduced-motion，不处理静态字号）。**具体建议优先「改纯图形」而非「放大字号」**：50% 缩放下 9→12px 仅得 6px 仍勉强，纯图形/色块更鲁棒——
- 富/铁角标：`L4663` 的 `label('富'/'铁',9)` 改为**高对比色块/图形**（富=金色菱形、铁=蓝灰方块，与 `L4653` 已有 tint 呼应），角标底色块放大到 ≥20×16；
