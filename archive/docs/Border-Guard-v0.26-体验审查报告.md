# 《边境守卫》v0.26 体验审查与实施记录

2026-11-14 · 审查基线 `f4de3bf9415f738a9249a72e7452924429bf4314`

## 玩家体验目标与范围

第一局要让玩家知道去哪建城、开发什么、哪边要守，以及每个动作发生了什么。五夜短局仍以白天发展领地与夜晚守城为主，领主参与探索、走位和战斗，居民把城堡和外围营地连接起来。正式立项候选里 45–90 分钟时长、扩张的必要性、三条专精路线都需要未来单独讨论。附带的 v0.11 草案记录了历史原型规则，其中的矿点面板阻断移动，与后来允许边看边走的要求有冲突，本轮遵循现行 Demo 与本次授权。

用户已确认的是界面、交互和表现可重做，保留原型规则及旧文件。桌面右侧和手机下方的非模态面板、命令分组、短反馈节奏与点敌判定是本轮实现决定。版本决策依据包括交接、候选立项、三份历史会话、v0.16–v0.25 的审查与更新记录及对应代码。历史中已被替换的方向包括以碎片解锁首领、无损转型、移动端普通短按默认打开建造面板。后两个选址占位、护送和碰撞相关修正通过现有脚本复查。

## 玩法审查与待决定事项

以下是对原规则的审查和后续提议，尚待用户决定。

- **白天决策。** 基础田、木、石、低产金矿需要花材料与行动，收益在天亮兑现。第 5 夜无普通收获，终局开发通常不能回本。v0.26 已把这个限制放进资源详情。种子 42 的塔防策略在首日用完 7 行动仍能过夜，第二日起常剩约 6–7 行动，时间与行动是否都形成有效约束还需要人玩。脚本主动提前入夜，其白天时长不能用来衡量等待感。
- **建筑与站位。** 塔可在射程内自动接敌，墙能让敌人停留、付出拆除时间，也会改变领主和居民可走的路。模拟的三局塔防均通关，但自动选近入口、没有对比等预算墙阵。现有证据说明塔防可用，不能判断塔比墙的长期优劣、两处城址是否同样合理、是否有固定最优套路。下一次可在同种子等预算下对比纯塔和塔墙混合。
- **领主与营地。** 单塔加领主脚本在第 5 夜失败，单营地脚本通关但有 3 名待援。脚本会把领主放在预定防守位置，并使用自动攻击和急修，未模拟真人持续换位、培养和夜间救援操作。因此无法据此断言领主流不可行或营地收益高。可在同种子下比较守家与经营一个营地的净收益、回本夜和失守风险，再决定是否需要讨论费用或敌人压力。
- **战斗参与和成长。** 夜战的主动动作目前主要是走位、攻击、齐射、药剂、急修和营救。测试证明判定可执行，尚无证据表明玩家会觉得每一波有事可做，或强化之间产生可感知的路线差异。保留现有规则，先观察玩家是否会在首夜主动改变站位、第二夜是否能说明上一夜的投资如何起效。
- **重玩与败局。** 军令、秘点、两处城址和提前召唤提供已存在的重玩理由。现有败局当夜的账本不关闭，仍保留实际损失事件；v0.26 沿用该结算口径。是否需要败局也显示完整分夜收支，需要独立规则决定。

## 已执行与待执行

1. 布局阶段执行脚本语法检查和坐标断言。浏览器启动受限，截图对照留给可启动浏览器的验收。
2. 交互阶段执行输入守卫、工具分派和点敌用例，并独立阅读 DOM、焦点、手势与夜战支援代码。复查后修正了暂停可聚焦、菜单点击穿透、旧手势与工具切换、受伤后按钮滞后。
3. 视觉阶段做 Canvas 代码与样式审查。战斗反馈和效果弱化使用现有机制，独立回归校验业务结果。像素观感、动画连贯性、音效和性能仍需实机。
4. 玩法阶段在 Node VM 运行两个版本的游戏脚本与既有测试。每版 168 项钩子断言，六组正常预算模拟结果一致，完成结算的夜次账本闭合。败局当夜未结账是原口径。模拟脚本有预设位置、揭雾与自动攻击，测试适配器未提供真实 DOM 版面、真实 Canvas 像素或音频。
5. 13 种视口的 v0.25 基线、v0.26 白天／详情／夜战截图和真实输入验收均待跑。浏览器脚本覆盖六种桌面、五种竖屏和两种横屏，并额外检查最窄支援栏和结算截图。启动失败证据独立保存，未生成占位截图。

下一次最值得验证的问题是：第一次玩的玩家能否在无人提示的情况下建城、开发一处材料来源并完成首夜布防。
